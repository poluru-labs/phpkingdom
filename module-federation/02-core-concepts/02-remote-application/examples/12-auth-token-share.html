Module Federation

// Remote Application — Example 12
// Focus: auth token share | Scenario: admin portal

// Remote = independently built app exposing modules via remoteEntry.js

const { ModuleFederationPlugin } = require("webpack").container;

module.exports = {
  output: { uniqueName: "products", publicPath: "auto" },
  devServer: { port: 3002, headers: { "Access-Control-Allow-Origin": "*" } },
  plugins: [
    new ModuleFederationPlugin({
      name: "products",
      filename: "remoteEntry.js",
      exposes: {
        "./ProductList": "./src/ProductList",
        "./ProductDetail": "./src/ProductDetail",
      },
      shared: {
        react: { singleton: true, requiredVersion: "^18.0.0" },
        "react-dom": { singleton: true, requiredVersion: "^18.0.0" },
      },
    }),
  ],
};
// Remotes can still run standalone for local development

Practice Notes

Checklist for Remote Application
- Practice: auth token share
- Scenario: admin portal
- Share framework runtimes as singletons with requiredVersion
- Load remotes lazily; wrap with error boundaries / fallbacks
- Deploy remotes independently; version remoteEntry URLs carefully
- Align CORS and CSP for cross-origin remoteEntry.js

Useful commands:
  npm install -D webpack webpack-cli webpack-dev-server
  # run host + remote on different ports
  npx webpack serve --config webpack.host.js --port 3000
  npx webpack serve --config webpack.remote.js --port 3002

Notes

This example shows one way to apply Remote Application in a admin portal context.

Keep remotes independently deployable, share carefully, and always plan for remote downtime.
