Module Federation

// Module Federation vs Monorepo — Example 25
// Focus: best practice recap | Scenario: profile remote

// Module Federation = runtime composition across independently deployed apps
// Monorepo = shared source / build-time packages (Nx, Turborepo, yarn workspaces)

// Monorepo package:
// import { Button } from "@acme/ui";  // compiled into each app

// Federated remote:
const { ModuleFederationPlugin } = require("webpack").container;
new ModuleFederationPlugin({
  name: "shell",
  remotes: { ui: "ui@https://cdn.example.com/ui/remoteEntry.js" },
});
// Shell loads Button at runtime — UI team deploys without rebuilding shell
// Use both: monorepo for shared libs, federation for team/runtime boundaries

Practice Notes

Checklist for Module Federation vs Monorepo
- Practice: best practice recap
- Scenario: profile remote
- Share framework runtimes as singletons with requiredVersion
- Load remotes lazily; wrap with error boundaries / fallbacks
- Deploy remotes independently; version remoteEntry URLs carefully
- Align CORS and CSP for cross-origin remoteEntry.js

Useful commands:
  npm install -D webpack webpack-cli webpack-dev-server
  # run host + remote on different ports
  npx webpack serve --config webpack.host.js --port 3000
  npx webpack serve --config webpack.remote.js --port 3002

Notes

This example shows one way to apply Module Federation vs Monorepo in a profile remote context.

Keep remotes independently deployable, share carefully, and always plan for remote downtime.
