Module Federation

// Rspack Module Federation — Example 04
// Focus: singleton share | Scenario: checkout remote

// Rspack Module Federation (webpack-compatible plugin API)

const { ModuleFederationPlugin } = require("@module-federation/enhanced/rspack");

module.exports = {
  entry: "./src/index.js",
  output: { uniqueName: "shell", publicPath: "auto" },
  plugins: [
    new ModuleFederationPlugin({
      name: "shell",
      remotes: {
        products: "products@http://localhost:3002/remoteEntry.js",
      },
      shared: {
        react: { singleton: true, requiredVersion: "^18.0.0" },
        "react-dom": { singleton: true, requiredVersion: "^18.0.0" },
      },
    }),
  ],
};

// Faster builds than webpack; MF 1.5/2.0 features via @module-federation/enhanced
// Align shared versions with remotes built by webpack or rspack

Practice Notes

Checklist for Rspack Module Federation
- Practice: singleton share
- Scenario: checkout remote
- Share framework runtimes as singletons with requiredVersion
- Load remotes lazily; wrap with error boundaries / fallbacks
- Deploy remotes independently; version remoteEntry URLs carefully
- Align CORS and CSP for cross-origin remoteEntry.js

Useful commands:
  npm install -D webpack webpack-cli webpack-dev-server
  # run host + remote on different ports
  npx webpack serve --config webpack.host.js --port 3000
  npx webpack serve --config webpack.remote.js --port 3002

Notes

This example shows one way to apply Rspack Module Federation in a checkout remote context.

Keep remotes independently deployable, share carefully, and always plan for remote downtime.
