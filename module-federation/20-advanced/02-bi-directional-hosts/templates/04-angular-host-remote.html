Module Federation

// Bi-Directional Hosts — Template 04
// Focus: angular host remote | Scenario: checkout remote

// Bi-directional: A consumes B and B consumes A — use sparingly

// app-a/webpack.config.js
new ModuleFederationPlugin({
  name: "appA",
  filename: "remoteEntry.js",
  exposes: { "./WidgetA": "./src/WidgetA" },
  remotes: { appB: "appB@http://localhost:3002/remoteEntry.js" },
  shared: { react: { singleton: true, requiredVersion: "^18.0.0" } },
});

// app-b/webpack.config.js
new ModuleFederationPlugin({
  name: "appB",
  filename: "remoteEntry.js",
  exposes: { "./WidgetB": "./src/WidgetB" },
  remotes: { appA: "appA@http://localhost:3001/remoteEntry.js" },
  shared: { react: { singleton: true, requiredVersion: "^18.0.0" } },
});

// Risks: circular init, unclear ownership, harder deploys
// Prefer shell → remotes; share via events/state bus if two-way UX needed

Practice Notes

Checklist for Bi-Directional Hosts
- Practice: angular host remote
- Scenario: checkout remote
- Share framework runtimes as singletons with requiredVersion
- Load remotes lazily; wrap with error boundaries / fallbacks
- Deploy remotes independently; version remoteEntry URLs carefully
- Align CORS and CSP for cross-origin remoteEntry.js

Useful commands:
  npm install -D webpack webpack-cli webpack-dev-server
  # run host + remote on different ports
  npx webpack serve --config webpack.host.js --port 3000
  npx webpack serve --config webpack.remote.js --port 3002

Notes

This template shows one way to apply Bi-Directional Hosts in a checkout remote context.

Keep remotes independently deployable, share carefully, and always plan for remote downtime.
