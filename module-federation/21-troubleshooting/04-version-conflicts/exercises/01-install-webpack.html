Module Federation

// Version Conflicts — Exercise 01
// Focus: install webpack | Scenario: e-commerce shell

// Shared dependency version conflicts

// Example: host react@18.2.0, remote react@17.0.2 + singleton
// → init may refuse or behave oddly with strictVersion

shared: {
  react: {
    singleton: true,
    requiredVersion: "^18.0.0",
    strictVersion: true,
  },
}

// Strategy:
// - Single major across all remotes (CI enforces)
// - Renovate/group updates for react
// - For non-singleton libs, duplicate copies may be OK (bundle cost)
// Read share-scope warnings — they name the conflicting package

Practice Notes

Checklist for Version Conflicts
- Practice: install webpack
- Scenario: e-commerce shell
- Share framework runtimes as singletons with requiredVersion
- Load remotes lazily; wrap with error boundaries / fallbacks
- Deploy remotes independently; version remoteEntry URLs carefully
- Align CORS and CSP for cross-origin remoteEntry.js

Useful commands:
  npm install -D webpack webpack-cli webpack-dev-server
  # run host + remote on different ports
  npx webpack serve --config webpack.host.js --port 3000
  npx webpack serve --config webpack.remote.js --port 3002

Notes

This exercise shows one way to apply Version Conflicts in a e-commerce shell context.

Keep remotes independently deployable, share carefully, and always plan for remote downtime.
